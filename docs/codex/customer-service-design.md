# 客服功能设计与实施清单

## 目标与已确认规则

- 店长是店铺聊天对象；店小二是店长的子账号。客户咨询店长时，客户看到店长，店长及店小二看到客户，店铺成员共享会话和历史消息，均可查看和回复。
- 店长及同店店小二之间可转接；转接改变当前接待人，不撤销其他店员的查看与回复权限。
- 店铺后台可以配置初始接待规则、每个客服接待上限、忙碌状态和活跃超时时间。接待量统计当前接待人名下、最后消息时间未超时的会话；超时自动释放容量。
- 无可接待客服或全部满员时，支持排队、分配给店长、允许超额分配，默认超额分配。排队客户应在客服可接待或有容量后按顺序重新分配。
- 客户侧展示店长身份；客服侧保留真实发送人，便于审计和协作。

## 现状与缺口

- 已有店长、店小二、共享会话生成、客服状态和转接入口；店小二绑定入口已补充实现。首次创建会话时，客户与店长或店小二无论哪一方发起，都创建客户、店长和现有店小二成员；客户成员的对方是店长。
- 转接不再主动隐藏其他客服会话；但尚缺持久化当前接待人、并发仲裁及可靠通知，不能视为完整转接。
- 原有客服状态是多设备 Redis 缓存；在线状态并不等同可接待状态，且现有读改写存在并发风险。会话共享成员数量不等于客服接待量。
- 客户联系店长和店小二的会话归一、补充成员、历史可见性、消息身份呈现和旧数据均须覆盖；不得改变已有客户端公开字段的含义。

## 设计约束

- Chat 业务位于本模块 Domain、Application、Contracts、EntityFrameworkCore；Host 只负责组合。复用现有 Session、SessionUnit、消息和权限机制。
- SQL Server 是接待分配和排队的可靠来源；Redis 是缓存或分布式协调手段。避免依赖进程内锁；每个店铺的分配和转接须跨实例串行化，并覆盖事务提交。
- 一条客户会话只能有一个当前接待记录；请求重试、消息重复、后台任务重试不得重复分配或重复入队。活动时间不得因乱序消息回退。
- 满员时的队列必须有可持久恢复的先后顺序、受控批次和索引；任务重试幂等，不能对消息大表或会话大表进行全表扫描。
- 活跃时间需要有明确的消息事实来源，并考虑系统命令、消息撤回、历史导入及消息写入失败；不可将转接命令本身误认为客户活动。
- 维持 SessionUnit 的 Redis Dirty / DB 写回、消息游标、DeletedRecorder 可见性、SignalR 多设备与多实例行为；不在每条消息路径引入不必要的数据库更新。
- 配置、排队和接待记录涉及数据库实体与索引。用户已要求生成 Migration 和执行数据库更新；更新前需核对数据库目标和全部待执行迁移。

## 客户端管理入口与实现方案（2026-11-21）

- 不建设独立 Web 管理后台。店铺客服管理同时放在 `F:\Dev\GotoIM\gotoim-flutter` 与 `F:\Dev\GotoIM\gotoim-electron`。
- 当前聊天身份的 `ChatObjectTypeEnums` 必须为 `ShopKeeper`（数值 7），消息页才显示“客服管理”入口；身份切换后立即重新判断。客户端隐藏入口只是交互控制，所有写操作仍由服务端校验店铺所有权。
- Flutter 入口位于 `SessionListPage` 的当前身份消息页头部，进入受控的客服管理页面；Electron 入口位于主窗口 `MainApp.vue` 的消息会话区域，进入主窗口路由或抽屉，不重建聊天视图，也不把管理状态混入其他身份的会话。
- 两端的客服管理页面包含：分配规则和满员策略配置、店员在线／忙碌及接待量、当前接待列表、排队列表及取消／人工出队、转接目标与操作反馈。店小二只保留共享聊天与转接能力；客户只看到排队与接待状态，不看到店员管理入口。
- 客服配置与接待量沿用现有 `ICallCenterAppService`。接待／排队列表、队列位置、店员容量和状态变化通知尚无完整契约，应先在 Chat 模块补带权限、游标分页、状态版本的 API，再接客户端。禁止从共享会话成员数或本地缓存推算接待量。
- Flutter 继续采用 UI → Riverpod → Repository → HTTP／SignalR；现有 `CallCenterApi` 仅覆盖转接，`ChatOwner` 当前没有可靠的数值 `objectType`，须从服务端读取并持久化数值类型后再用于入口判断。Electron 复用已有 `ChatOwnerDto.objectType`（数值 7），遵守 Main 统一 SignalR、Renderer 使用短期令牌请求业务 API 的边界。
- 先实现同一套后端查询与通知契约，再分别完成 Flutter 和 Electron 页面；验收身份切换、配置授权、列表分页、排队恢复、转接、断线重连、旧客户端消息兼容，以及移动端与 Windows 桌面端实际操作。Electron 当前未提交的数据库和消息改动、Flutter 当前生成文件改动都要保留。

### 掌柜消息页交互

1. 当前身份切换为掌柜后，在会话搜索区显示“客服管理”入口；切换到客户或店小二立即隐藏。页面打开后如身份发生切换，应关闭管理页并清除该店铺的临时状态。
2. 管理页顶部显示本店活跃接待数、排队数、在线／忙碌店员数；下方分为“接待中”“排队中”“店员”“分配设置”。接待和排队使用服务端游标分页，不从本地消息列表推算。
3. “分配设置”编辑分配策略、在线要求、最大接待量、活跃超时及满员策略；保存后读回服务端配置。提供恢复默认设置操作，操作前展示影响范围。
4. “接待中”可查看当前负责人并转接给店长或本店店小二；“排队中”可取消或触发调度。转接成功后刷新负责人和计数，不改变共享会话成员或消息发送通道。
5. 网络恢复或 SignalR 重连时重新拉取当前页和计数。实时事件只作为刷新提示，以数据库中的配置、接待和队列记录为准。

### 接口与权限边界

| 能力 | 现有服务端接口 | 客户端实现要求 |
| --- | --- | --- |
| 读取／保存／重置配置 | `GetConfigurationAsync`、`UpdateConfigurationAsync`、`DeleteConfigurationAsync` | 仅掌柜入口可见，服务端再次校验店铺归属；保留默认满员策略“允许超额分配” |
| 当前接待量 | `GetActiveCountsAsync` | 展示店员负载，统计口径为最后活动时间和配置超时 |
| 单会话负责人／转接 | `GetAssignmentAsync`、`TransferToAsync` | 沿用现有转接接口，操作后按服务端状态刷新 |
| 队列调度／取消 | `DrainQueueAsync`、`CancelQueueAsync` | 仅在操作被授权时展示，重复点击需幂等 |
| 接待和排队总览 | 尚缺分页列表、队列位置与状态通知契约 | 后端补齐后再提供完整列表，不使用无界查询或客户端拼接 |

### 两端落点

- Flutter：`SessionListPage` 的 `CurrentOwnerHeader` 增加掌柜专属入口；补 `ChatOwner.objectType` 数值的 JSON／本地持久化链路，不能用本地化的 `objectTypeDescription` 判身份；管理页继续走 Riverpod、Repository 和现有 Dio 登录态。
- Electron：`MainApp.vue` 消息会话区搜索栏旁增加掌柜专属入口；读取已有 `ChatOwnerDto.objectType`；管理页沿用主窗口路由／抽屉，业务请求复用现有认证与 API 基址，SignalR 继续由 Main 统一维护。
- 两端保持同一字段含义和错误处理：无权访问、店员离线、容量变化、并发转接、会话已出队时展示服务端最新状态；旧客户端仍可正常收发共享会话消息。
