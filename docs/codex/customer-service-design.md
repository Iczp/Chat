# 客服功能设计与实施清单

## 目标与已确认规则

- 店长是店铺聊天对象；店小二是店长的子账号。客户咨询店长时，客户看到店长，店长及店小二看到客户，店铺成员共享会话和历史消息，均可查看和回复。
- 店长及同店店小二之间可转接；转接改变当前接待人，不撤销其他店员的查看与回复权限。
- 店铺后台可以配置初始接待规则、每个客服接待上限、忙碌状态和活跃超时时间。接待量统计当前接待人名下、最后消息时间未超时的会话；超时自动释放容量。
- 无可接待客服或全部满员时，支持排队、分配给店长、允许超额分配，默认超额分配。排队客户应在客服可接待或有容量后按顺序重新分配。
- 客户侧展示店长身份；客服侧保留真实发送人，便于审计和协作。

## 现状与缺口

- 已有店长、店小二、共享会话生成、客服状态和转接入口；店小二绑定入口已补充实现。首次创建会话时，客户与店长或店小二无论哪一方发起，都创建客户、店长和现有店小二成员；客户成员的对方是店长。
- 转接不再主动隐藏其他客服会话；但尚缺持久化当前接待人、并发仲裁及可靠通知，不能视为完整转接。
- 原有客服状态是多设备 Redis 缓存；在线状态并不等同可接待状态，且现有读改写存在并发风险。会话共享成员数量不等于客服接待量。
- 客户联系店长和店小二的会话归一、补充成员、历史可见性、消息身份呈现和旧数据均须覆盖；不得改变已有客户端公开字段的含义。

## 设计约束

- Chat 业务位于本模块 Domain、Application、Contracts、EntityFrameworkCore；Host 只负责组合。复用现有 Session、SessionUnit、消息和权限机制。
- SQL Server 是接待分配和排队的可靠来源；Redis 是缓存或分布式协调手段。避免依赖进程内锁；每个店铺的分配和转接须跨实例串行化，并覆盖事务提交。
- 一条客户会话只能有一个当前接待记录；请求重试、消息重复、后台任务重试不得重复分配或重复入队。活动时间不得因乱序消息回退。
- 满员时的队列必须有可持久恢复的先后顺序、受控批次和索引；任务重试幂等，不能对消息大表或会话大表进行全表扫描。
- 活跃时间需要有明确的消息事实来源，并考虑系统命令、消息撤回、历史导入及消息写入失败；不可将转接命令本身误认为客户活动。
- 维持 SessionUnit 的 Redis Dirty / DB 写回、消息游标、DeletedRecorder 可见性、SignalR 多设备与多实例行为；不在每条消息路径引入不必要的数据库更新。
- 配置、排队和接待记录涉及数据库实体与索引。用户已要求生成 Migration 和执行数据库更新；更新前需核对数据库目标和全部待执行迁移。

1. 明确并实现店铺级配置和授权管理：分配策略、在线／忙碌条件、每客服上限、活跃超时时间及满员策略。
2. 持久化接待人及队列状态，建立唯一约束和按店铺、状态、接待人、活动时间、排队顺序查询所需索引。
3. 接入客户首次咨询和超时后重新咨询：同一会话幂等分配；实现在线优先、容量检查与超额、店长兜底和排队策略。
4. 客服状态／容量变化及超时释放后，分批、按顺序调度队列；故障和多实例重试可恢复。
5. 将转接接入同一套接待记录与并发控制，保证同店校验、授权、共享可见性和通知一致性。
6. 核实客户侧店长身份、店员真实身份、历史消息和 DeletedRecorder；补齐新店员加入已有会话及旧数据兼容。
7. 测试配置授权与校验、三种兜底、活跃超时、容量、消息乱序、并发首次分配与转接、队列重试、跨店越权、共享会话和多设备状态。
8. 编译受影响项目，运行相关自动化测试，检查最终 diff；记录未生成的 Migration、Redis 3.2 兼容和运行环境限制。

## 当前实现进度

### 2026-11-20 本轮实施（待完整验收）

- 配置读写接口已开放，并增加删除店铺配置后回退到默认配置；参数范围和枚举由 DTO 与领域对象双重校验。后台可查询每位店员的活跃接待量。
- 新增已提交消息的分布式事件处理器，按店铺分布式锁更新唯一接待记录；系统命令不计入活动。当前每条客服会话消息会产生一次接待记录数据库读写，需在生产量级评估写入成本。
- 首次客户咨询尝试按配置自动分配；`Pending` 等非 `Online` 状态不参与要求在线的候选人。超时容量由最后活动时间窗口计算，过期后再有新消息可重新分配。队列按持久化入队时间排序。
- 转接在店铺分布式锁及独立事务中更新当前负责人，现有共享成员仍可查看和发送，已有转接命令继续用于通知。
