# 创建群与邀请成员：事务及 Redis 验证

日期：2026-11-10，本地开发库 Chat_Module_v3。

## 处理方式

创建群 / 邀请成员复用事务性 ABP 工作单元，保存成员后写入 Redis 会话单元及连接池，再在相同 SQL 事务中创建系统消息和分配 SessionSeq。成员缓存与消息缓存的写入任务会等待完成。普通异常或 SQL 回滚时尝试清理本次新增的会话单元、连接池和消息缓存；连接池使用 Redis 3.2 Lua 原子合并 owner，使用单次事务标记识别需要撤回的 owner，避免覆盖其他账号及损失 Int64 精度。

系统消息在数据库提交期间对会话读取窗口设置短期保护标记并使旧窗口失效。标记存在时读取回源 SQL，不发布窗口。提交或回滚后尝试清除标记；提交后清理出错不会让已提交的邀请返回失败，标记仍在时继续回源，标记最长保留 24 小时。没有新增 Chat_RoomCompletion 数据库表。

- 临时 API 使用真实账号所属的测试对象 6133、6134。最终镜像先建群 6160；对该群分别注入读取窗口、连接池和消息索引 Redis 类型错误，三次请求均返回 500，SQL 始终保持原 2 个单元、1 条消息和 SessionSeq 1；测试键和临时连接恢复，新增成员索引未保留。恢复后并发邀请 6134，一次 200、一次 409；SQL 仅有一个被邀请单元，3 个单元、2 条消息，LastMessageSeq 与最大 SessionSeq 为 2；Redis 成员和消息数也分别为 3、2，保护标记已清除。
- 使用真实账号创建时包含 6134 的群 6158：SQL 有 3 个单元、1 条系统消息和 SessionSeq 1。由于现有创建输入校验要求列表长度大于 2，测试请求重复传入创建者 ID；业务层过滤创建者后实际成员只有测试对象 6133、6134。

## 数据与限制

测试群 6155 至 6161 保留在开发库；未删除先前压测会话或其消息。临时测试容器和故障注入键已清理 / 恢复。

SQL Server 和 Redis 不具有跨系统原子事务。进程在 Redis 写入后、SQL 回滚清理执行前崩溃，或 Redis 持续不可用使清理本身失败时，成员缓存或连接池仍可能残留；当前只记录错误，没有持久化补偿任务。消息读取窗口保护标记只确保该场景的读取回源，不修复全部其他缓存。必须以 SQL 为最终依据；不要将本次普通故障测试解释为进程崩溃场景的严格原子性保证。
